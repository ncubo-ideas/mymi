15 · Recetas: ¿cómo hago para…?

Las preguntas concretas que todo equipo hace al adoptar Puppeteer, resueltas paso a paso.

15.1 · Modificar una app que ya funciona

Este es el titular de la guía, y conviene verlo con código real. Supón una app que ya lleva las existencias de una bodega: sabe Ingresar y Retirar. Nos piden registrar devoluciones. La modificación completa es un método nuevo en el dominio + una línea de DSL:

C# · dominio (diff)  public void Retirar(int cantidad) { /* … ya existía … */ }

+ public void Devolver(int cantidad)
+ {
+     if (cantidad <= 0) throw new LanguageException("la cantidad debe ser positiva");
+     _existencias = _existencias + cantidad;
+ }

Y en el punto donde se necesita, una sola línea de DSL:

DSL (diff)+ b.Devolver(@n);

Eso es todo. No hubo que tocar migraciones, ni sincronizar un read-model, ni coordinar con las decenas de otros comandos: cada comando es un hecho independiente en el diario. La app corriendo, con la devolución ya integrada:

Salida realb.Ingresar(100); b.Retirar(30); b.Devolver(5);
existencias -> {"existencias":75}
✓ Haz

Al pensar una funcionalidad nueva, pregúntate primero ¿qué verbo de dominio expresa este hecho? Si el verbo captura el hecho, la integración suele ser esa única línea de DSL. Modelar el hecho —no el flujo de pantallas— es lo que mantiene el cambio barato.

15.2 · Agregar una base de datos a la arquitectura

Dónde vive el diario es una decisión de configuración, no de arquitectura. La lógica de negocio no cambia ni una línea. Pasar de memoria a disco es cambiar el backend en ConfigureStorage:

C# (diff)- actor.ConfigureStorage(DatabaseType.IN_MEMORY, "bodega");
+ actor.ConfigureStorage(DatabaseType.FileSystem, "path=C:\\datos\\bodega");

Y de disco a una base relacional es el mismo gesto, apuntando al backend SQL (a través del adapter Ncubo.Puppeteer.Adapters.Sql):

C#actor.ConfigureStorage(DatabaseType.SQLServer, "<connection string>");

Los mismos comandos, el mismo dominio, el mismo diario — solo cambia dónde se persiste. Es exactamente lo que verificamos en el Cap. 7: el actor “renacido” sobre el diario en disco reconstruye el estado idéntico. Elige el backend según tu necesidad:

BackendCuándo
IN_MEMORYPruebas, ejemplos, cachés efímeros.
FileSystemApps locales / por instancia; un diario por carpeta.
SQLServer · MySQLPersistencia relacional centralizada.
PlainTextDiario legible/editable por herramientas.
 Tabla 17. El “dónde persiste” es configuración; la lógica no se entera.
✎ Nota del diseñador

Para leer desde una base BI (una tabla que no puede perder filas) no cambies el backend del diario: agrega una reacción con Outbox.Emit hacia esa base (Cap. 9, 14). El diario sigue siendo la verdad; la tabla BI es una proyección durable alimentada por reacciones.

15.3 · Migrar un sistema legado a Puppeteer

No se migra de un salto; se estrangula el legado poco a poco, dejando que el diario se vuelva la verdad de forma incremental:

  1. Envuelve la capacidad tras un actor. Pon una fachada (como el FestivalJournal del bingo) delante de la capacidad legada; toda operación entra ahora como un comando al actor.
  2. Journaliza cada operación como comando. Aunque al principio el comando solo delegue al código viejo, el diario ya empieza a registrar los hechos en orden — ganas auditoría y replay desde el día uno.
  3. Mueve la lógica al dominio C#, verbo por verbo. Reemplaza la delegación al legado por lógica de dominio propia, una operación a la vez. El contrato (el comando) no cambia para quien llama.
  4. Convierte las lecturas en queries y proyecciones. Las consultas pasan a PerformQuery/print; los read-models que el legado mantenía a mano pasan a reacciones (Outbox/Program.Emit).
  5. Apaga el legado cuando el actor cubre todas las operaciones. El diario ya es la fuente de verdad completa.
~ Considera

Durante la transición puedes correr ambos en paralelo y comparar: el diario del actor te da una traza objetiva de cada hecho, ideal para validar que el nuevo dominio reproduce el comportamiento del legado antes de apagarlo.

Lo que aprendiste

  • Modificar una app viva ≈ un verbo de dominio + una línea de DSL; cada comando es un hecho independiente.
  • Agregar una base de datos es cambiar el backend en ConfigureStorage; la lógica no cambia. Para BI, una reacción con Outbox.
  • Migrar un legado se hace estrangulando: fachada → journalizar → mover lógica → proyectar lecturas → apagar.

Con esto cierra el borrador de la guía: entendiste el paradigma, escribiste actores, cruzaste fronteras entre ellos y bajaste a patrones y recetas. Los anexos (glosario, convenciones del DSL y la referencia consolidada de recomendaciones) se desarrollarán tras esta ronda de revisión.
