5 · Control de flujo y guardas

Ramas y bucles dentro del cuerpo, y la guarda Check que rechaza un comando sin dejar rastro.

Una regla de oro guía todo este capítulo: una decisión = un comando. La lógica de qué hacer vive dentro del script, no repartida entre varios Perform en tu C#. Así, el comando persistido captura la decisión completa.

5.1 · if / else en el cuerpo

Ramifica dentro del script. Cualquier sentencia compone dentro de un if, también una llamada a verbo:

DSLif (aforo.Cabe(@n)) { aforo.Tomar(@n); }
Salida real{"t":2}
✕ No hagas

No partas la decisión en tu C# (if (x) actor.Using(A) else actor.Using(B)). El camino “no hace nada” deja un comando vacío o ausente en el diario, y la decisión queda fuera del actor. Pon la rama dentro de un solo cuerpo.

5.2 · foreach

Itera una colección dentro del mismo comando — toda la iteración es un solo hecho en el diario:

DSLforeach (x in @nums) { if (aforo.Cabe(x)) { aforo.Tomar(x); } }
Salida real{"t":4}

El bingo lo usa al vender: por cada cartón vendido, lo pone en juego, todo en el mismo comando:

DSL · realforeach (numero in @cartones) { mesa.PutCardInPlay(numero); }

5.3 · Check: la guarda transaccional

Cuando un comando debe correr solo si una condición se cumple, y quien llama necesita enterarse del rechazo, se usa una guarda Check con la variante de dos cuerpos (guarda + comando) y PerformCheckThenCommand():

C#actor.Using("Check(aforo.Cabe(@n)) Error 'sin cupo';", "aforo.Tomar(@n);")
     .WithParameters(p => p["n", typeof(int)] = 1)
     .PerformCheckThenCommand();

El contrato de retorno: vacío = aceptado (el comando corrió y se persistió); no vacío = rechazado, y trae los motivos. Al rechazar, nada se persiste:

Salida realCheck acepta -> return=""          (vacio = aceptado)
Check rechaza -> return="{"EWI":[{"Error":"sin cupo"}]}"

Corre en dos fases: primero bajo un candado de lectura (si falla, devuelve el motivo y no persiste nada); si pasa, vuelve a comprobar bajo el candado de escritura y recién ahí corre y persiste el comando. Solo una severidad de falla bloquea:

Severidad¿Bloquea el comando?
Error, WarningSí — no persiste nada, devuelve el motivo
Information, MessageNo — es informativa, el comando corre igual
 Tabla 10. Severidades de Check: solo las de falla detienen el comando.

Así encadena el bingo varias guardas antes de vender, cada una con su mensaje:

DSL · realCheck(festival.ErrandLetsThemDo(@marca, @quien, @oficio))
    Error 'ese papelito no es tuyo o ya no esta vigente';
Check(festival.MerchantCanSellThem(@marca, @cartones))
    Error 'esos cartones ya no los tenes en la mano';
✕ No hagas

No pongas efectos secundarios en una guarda: debe ser un predicado puro (lee para decidir, no muta). Recuerda que el cuerpo de Check puede correr dos veces (pre-check y re-check); un efecto colateral se dispararía dos veces.

✎ Nota del diseñador

¿Cuándo Check y cuándo un if simple? Usa Check cuando un intento rechazado no debe dejar entrada en el diario (un if que no hace nada igual persiste un comando), o cuando quieres el pre-chequeo optimista bajo candado de lectura. Para lo demás, un if basta.

Lo que aprendiste

  • Una decisión = un comando: la rama vive en el cuerpo, no en tu C#.
  • if/else y foreach componen cualquier sentencia, incluidas llamadas a verbos.
  • Check rechaza sin dejar rastro; retorno vacío = aceptado, no vacío = motivos.
  • Solo severidades Error/Warning bloquean; la guarda debe ser pura.
