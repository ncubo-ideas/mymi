2 · Tu primer actor

De cero a un actor que guarda estado, ejecuta comandos y responde queries — con código que compila y corre.

Con el modelo mental fresco, construyamos dos actores minúsculos. El primero es lo más simple posible: un contador. El segundo introduce un objeto de dominio con verbos. Los fragmentos de esta sección son recortes; cómo correrlos y su código está en el Anexo A.

2.1 · El actor más simple

Crear un actor son dos líneas: darle un nombre y decirle dónde guarda su diario (aquí, en memoria).

C#var actor = new ActorV2("contador", typeof(PrimerActor).Assembly);
actor.ConfigureStorage(DatabaseType.IN_MEMORY, "contador");

Ahora le mandamos comandos. Un comando cambia el estado y se persiste solo. Fíjate en que cada comando ve lo que dejó el anterior: el estado persiste entre comandos.

C#actor.Using("counter = 0;").PerformCommand();
actor.Using("counter = counter + 1;").PerformCommand();
actor.Using("counter = counter + 1;").PerformCommand();

Para leer sin cambiar nada, usamos una query. El verbo print del DSL emite un valor con una etiqueta, y la query devuelve esa salida como JSON:

C#string salida = actor.Using("print counter 'valor';").PerformQuery();
Salida real{"valor":2}

Eso es todo: un actor que nace, recibe órdenes, guarda su estado y lo reporta. No escribimos SQL, no abrimos conexiones, no serializamos nada a mano. Ya viste en el capítulo anterior por qué funciona; esta es la mecánica.

2.2 · Un objeto de dominio con verbos

Un contador es útil para arrancar, pero la lógica real vive en tus clases de dominio en C#. El DSL las construye y llama sus verbos. Modelemos un torniquete: empieza bloqueado, una moneda lo desbloquea, y al empujar deja pasar una vez y vuelve a bloquearse.

Lo esencial del dominio: el estado es privado y solo cambia a través de verbos. El objeto es dueño de su invariante —no se puede pasar sin moneda—:

C# · dominiopublic class Torniquete
{
    private bool _desbloqueado;
    private int _pasos;

    public void InsertarMoneda() { _desbloqueado = true; }

    public void Empujar()
    {
        if (!_desbloqueado)
            throw new LanguageException("El torniquete esta bloqueado: inserte una moneda.");
        _pasos = _pasos + 1;
        _desbloqueado = false;
    }

    // Queries totales: nunca lanzan, siempre tienen respuesta.
    public bool Desbloqueado => _desbloqueado;
    public int  Pasos       => _pasos;
}

Desde el DSL, lo construimos y lo dejamos en el estado raíz; luego llamamos sus verbos en comandos separados:

DSLt = Torniquete();   // se queda en el estado raiz del actor
t.InsertarMoneda();
t.Empujar();

Y consultamos su estado con una query que emite dos valores:

DSL{ print t.Desbloqueado 'desbloqueado'; print t.Pasos 'pasos'; }
Salida real{"desbloqueado":false,"pasos":1}

Insertamos una moneda y empujamos una vez: el torniquete quedó de nuevo bloqueado (false) y registró un paso. El invariante se respetó sin que nosotros lo verificáramos desde afuera: vive dentro del objeto.

✓ Haz

Expón el dominio como verbos que representan operaciones (InsertarMoneda, Empujar) y queries totales que siempre responden (Pasos). Deja que cada objeto proteja sus propias reglas.

! Evita

Evita setters públicos que dejen fijar el estado desde afuera (t.Desbloqueado = true). Rompen el invariante y convierten al objeto en una bolsa de datos. Un cambio de estado siempre debería pasar por un verbo con sentido de negocio.

✎ Nota del diseñador

Este estilo —verbos que cambian el estado, propiedades que solo leen— es exactamente el del dominio del bingo que viste en el capítulo anterior: su clase BingoGame, con verbos como PutCardInPlay o RegisterDraw y queries totales como DrawnCount. El torniquete es ese mismo patrón, en miniatura.

Lo que aprendiste

  • Un actor se crea con un nombre y un almacenamiento; le hablas con Using(script) y PerformCommand() / PerformQuery().
  • Los comandos cambian el estado (y se persisten); las queries solo leen.
  • El estado persiste entre comandos; los identificadores de nivel superior son el estado raíz.
  • Tu dominio en C# lleva la lógica y los invariantes; el DSL lo orquesta.

Con esto ya escribes y consultas actores, y entiendes el modelo que hay debajo. A partir del próximo capítulo entramos de lleno al DSL —literales, expresiones, @Now, variables locales y el bloque upgrade— y luego a los parámetros, las guardas y el dominio.
